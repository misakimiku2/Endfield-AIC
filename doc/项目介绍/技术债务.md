## 技术债务分类

### 一、架构与设计债务 (P0-P1)

#### TD-001: 缺乏 app 级统一状态管理方案
**严重程度**: P0（高）

**问题描述**:
- 项目在 `pubspec.yaml` 引入了 `provider: ^6.1.1` 依赖，但**全项目未实际使用**（无 `import 'package:provider'`、无 `MultiProvider`、无 `context.watch`）
- UI 状态主要通过原始 `setState` 管理，实测全项目 **108 处** setState 调用（`canvas_editor.dart` 27、`building_detail_dialog.dart` 14、`editor_page.dart` 14 为主）
- 需要说明的是：项目**已用** `ChangeNotifier` 管理仿真引擎（`SimulationEngine extends ChangeNotifier`，`editor_page.dart` 通过 `addListener` 手动消费 tick），但这只覆盖仿真数据，app 级状态（项目、选区、设备放置等）仍依赖 setState + 回调
- 状态共享通过回调函数层层传递，例如 `CanvasEditor` widget 暴露了一组回调：

**影响**:
```dart
// lib/canvas/canvas_editor.dart - CanvasEditor 的回调属性
class CanvasEditor extends StatefulWidget {
  final ValueChanged<ProjectState> onProjectChanged;
  final VoidCallback? onBuildingPlaced;
  final ValueChanged<PlacedBuilding?>? onBuildingSelected;
  final ValueChanged<String>? onErrorToast;
  // ...
}
```

**建议解决方案**:
```dart
// 建议做法 - Provider 状态管理
class ProjectProvider extends ChangeNotifier {
  ProjectState _project = ProjectState();
  // 状态统一管理
}

// 在顶层注册
MultiProvider(
  providers: [
    ChangeNotifierProvider(create: (_) => ProjectProvider()),
    ChangeNotifierProvider.value(value: simulationEngine),
  ],
  child: MaterialApp(...),
)

// 在子组件中访问
final project = context.watch<ProjectProvider>();
```

**预期收益**:
- 状态更新自动传播到所有依赖组件
- 显著减少 setState 调用与回调层数
- 代码更简洁、可测试性更高

**工作量估计**: 3-5 天

#### TD-002: 数据模型与业务逻辑混杂
**严重程度**: P1（中高）

**问题描述**:
- `PlacedBuilding`（`lib/models/project.dart`）同时包含纯数据字段与大量业务逻辑方法
- 输入/输出库存的增删校验（`acceptInputItem`/`consumeInputItems`/`addOutputItem` 等）、分流器/汇流器/物流桥的中转机制（`acceptIntoBuffer`/`acceptBridgeInputItem` 等）、端口连接判断（`conveyorPortConnections`）全部内聚在模型类中
- 模型类承担了过多职责，既难以作为纯数据结构序列化，也使单元测试需要构造完整对象

**代码位置**:
```dart
// lib/models/project.dart - PlacedBuilding 类（节选）
class PlacedBuilding {
  // 数据字段
  final String id;
  final Building building;
  double gridX;
  double gridY;
  int rotation;
  Map<String, int> outputItems;
  // ... 更多数据字段

  // 业务逻辑方法（与数据字段混杂在同一类）
  bool acceptInputItem(String itemId) { ... }
  bool consumeInputItems(String itemId, int amount) { ... }
  bool acceptIntoBuffer(String itemId, String direction) { ... }   // 分流器
  bool acceptBridgeInputItem(String itemId, String outputDirection) { ... } // 物流桥
  Map<String, bool> conveyorPortConnections(...) { ... }           // 端口连接
}
```

> 说明：UI 状态（如 `_isLongPressing`、`_hoveredBuilding`）已正确放在 `_CanvasEditorState` 中，与模型分离，此处不构成问题。端口连接的**计算逻辑**已集中在 `PlacedBuilding.conveyorPortConnections`，但其**缓存管理**分散在 `canvas_editor.dart`（见 TD-006）。

**建议解决方案**:
1. 分离纯数据模型与业务逻辑
2. 创建专门的 Repository/Service 处理业务逻辑
3. 模型仅保留字段与简单的数据校验

**预期收益**:
- 模型可独立测试
- 业务逻辑可复用
- 减少模型类的复杂度

**工作量估计**: 2-3 天

### 二、代码质量债务 (P1-P2)

#### TD-003: 代码重复严重
**严重程度**: P1（中高）

**问题描述**:
- `PortState.worldPosition` 和 `PortState.gridPosition` 两个方法（`lib/models/project.dart:20-109`）约 40 行主体逻辑完全相同，仅末行返回值不同
- 旋转矩阵计算逻辑重复

**代码位置**:
```dart
// lib/models/project.dart - 两个方法主体完全一致
Offset worldPosition(double gridX, double gridY, double cellSize,
    int gridWidth, int gridHeight, {int rotation = 0}) {
  // ... 约 40 行相同的 localGrid/旋转/坐标转换逻辑 ...
  return Offset(wx * cellSize, wy * cellSize);  // 唯一区别：乘以 cellSize
}

Offset gridPosition(double gridX, double gridY, int gridWidth, int gridHeight,
    {int rotation = 0}) {
  // ... 约 40 行完全相同的转换逻辑 ...
  return Offset(wx.floorToDouble(), wy.floorToDouble());  // 唯一区别：取整
}
```

**建议解决方案**:
```dart
// 提取公共方法
Offset _calculatePortPosition({
  required double gridX,
  required double gridY,
  required int gridWidth,
  required int gridHeight,
  required bool returnWorldCoords,
  double cellSize = 48.0,
  int rotation = 0,
}) {
  // 统一的转换逻辑
  final pos = _transform(/* ... */);
  return returnWorldCoords
    ? Offset(pos.dx * cellSize, pos.dy * cellSize)
    : Offset(pos.dx.floorToDouble(), pos.dy.floorToDouble());
}
```

**预期收益**:
- 消除约 40 行重复代码（这两个方法）
- 降低维护成本和 bug 风险

#### TD-004: JSON 解析缺乏类型安全封装
**严重程度**: P2（中）

**问题描述**:
- JSON 解析处大量使用 `(json['key'] as num).toDouble()` 强制转换，无默认值、无错误提示
- 实测全项目约 **21 处**，集中在 `editor_page.dart`（8 处）与 `canvas/sim_protocol.dart`（8 处），以及 `building.dart`/`recipe.dart`/`sim_worker.dart`
- 运行时类型错误风险高（数据缺字段或缺类型时直接抛异常）

**代码位置**:
```dart
// lib/models/building.dart
relativeX: (json['relative_x'] as num).toDouble(),
relativeY: (json['relative_y'] as num).toDouble(),

// lib/models/recipe.dart
processTimeSeconds: (json['process_time_seconds'] as num).toDouble(),

// lib/canvas/sim_protocol.dart / lib/pages/editor_page.dart
gridX: (json['gridX'] as num).toDouble(),
```

**建议解决方案**:
```dart
// 创建类型安全的扩展方法
extension JsonDouble on Map<String, dynamic> {
  double getDouble(String key, [double defaultValue = 0.0]) {
    final value = this[key];
    if (value == null) return defaultValue;
    if (value is double) return value;
    if (value is int) return value.toDouble();
    if (value is num) return value.toDouble();
    throw FormatException('Expected double for key $key, got ${value.runtimeType}');
  }
}

// 使用
relativeX: json.getDouble('relative_x'),
```

**预期收益**:
- 提高类型安全性
- 更早发现数据格式错误
- 代码更简洁

**工作量估计**: 1 天

### 四、性能债务 (P2)

#### TD-006: 端口连接缓存需手动触发
**严重程度**: P2（中）

**问题描述**:
- `_rebuildPortConnectionsCache()`（`lib/canvas/canvas_editor.dart:118`）需要在多处手动调用，实测至少在 8 处触发（建筑放置、移动、删除、旋转、传送带创建等）
- 容易遗漏导致状态不一致
- 每次重建全量计算，性能浪费

**代码位置**:
```dart
// lib/canvas/canvas_editor.dart
void _rebuildPortConnectionsCache() {
  portConnectionsCache = {};
  for (final pb in _project.buildings) {
    portConnectionsCache[pb.id] = pb.conveyorPortConnections(
      _project.conveyors, ...);
  }
}

// 在多处手动调用（节选）
void initState() { ... _rebuildPortConnectionsCache(); }
void _onBuildingPlaced() { ... _rebuildPortConnectionsCache(); }
```

**建议解决方案**:
```dart
// 实现自动缓存机制
class PortConnectionCache {
  final ProjectState _project;
  Map<String, Map<String, bool>> _cache = {};
  int _projectVersion = 0;

  Map<String, bool> get(String buildingId) {
    if (_project.version != _projectVersion) {
      _rebuild();  // 自动检测并重建
    }
    return _cache[buildingId] ?? {};
  }

  void invalidate(String buildingId) {
    _cache.remove(buildingId);  // 精细失效
  }
}
```

**预期收益**:
- 减少全量重建次数
- 避免缓存不一致 bug
- 自动化维护

**工作量估计**: 2 天

### 五、平台兼容债务 (P2)

#### TD-008: Isolate 处理逻辑复杂 ✅ 已解决
**严重程度**: P2（中）

**状态**: 已解决。引入 `SimulationBackend` 抽象，将 Isolate 编排与主线程回退拆为两个独立后端。

**问题描述（已修复）**:
- Web 平台不支持 Isolate，需要单独处理。
- 原 `SimulationEngine`（552 行）把原生 Isolate 编排（spawn/握手/消息收发/增量合并）
  与 Web 主线程回退逻辑（`_fallback*` 系列约 10 个方法）混杂在同一类内。
- 回退模式代码路径复杂，难以测试；同时存在死代码（`_fallbackProduceDepotOutput`、
  `_fallbackPushOutputToBelts`、`_outputItemIdForBeltStart`、`_beltEnd`、`SimControlMessage` 等）。

**实际解决方案**:

抽象后端接口（`lib/canvas/simulation_backend.dart`）：
```dart
abstract class SimulationBackend {
  bool get isReady;
  Future<void> init();
  void attach(ProjectState project);
  void start();
  void stop();
  void setSpeed(double multiplier);
  void syncState(int revision, ProjectState project, DataLoader loader, double speedMultiplier);
  void dispose();
}
```

两个实现：
- `lib/canvas/main_thread_simulation_backend.dart`：Web 平台 / Isolate 不可用时的回退，
  直接在主线程推进 `ProjectState`。暴露 `debugTickForTesting(dt)` 供测试。
- `lib/canvas/isolate_simulation_backend.dart`：原生平台用独立 Isolate 计算，
  含 spawn、握手、`_syncState`、增量合并 `_applyTickResult`。

`SimulationEngine` 瘦身为协调者（`lib/canvas/simulation_engine.dart`，~120 行）：
```dart
class SimulationEngine extends ChangeNotifier {
  late final MainThreadSimulationBackend _mainBackend;       // 始终存在（Web 唯一路径 / 原生过渡窗口）
  IsolateSimulationBackend? _isolateBackend;                 // 仅原生平台

  SimulationEngine(this._dataLoader) {
    _mainBackend = MainThreadSimulationBackend(_dataLoader, _onBackendChanged);
    if (!kIsWeb) {
      _isolateBackend = IsolateSimulationBackend(_dataLoader, _onBackendChanged);
    }
  }
  // attach/start/stop/setSpeed 委托给后端，自身只负责 isRunning / speedMultiplier / notifyListeners
}
```

**行为保持**:
- 公共 API（`isRunning`/`speedMultiplier`/`attach`/`start`/`stop`/`toggle`/`init`/`dispose`）签名不变，
  消费方（`main.dart`、`editor_page.dart`、`canvas_editor.dart` 的 `context.watch<SimulationEngine>()`、
  `ProjectNotifier`）零改动。
- 原生平台 Isolate 握手前的过渡窗口仍由主线程后端兜底，与旧实现一致。

**死代码清理**（本次一并完成）:
- engine 的 `_fallbackProduceDepotOutput` / `_fallbackPushOutputToBelts` / `_outputItemIdForBeltStart`
  / `_fallbackLogCounter` / `_hasOutputSpace`（仓库取货与输出推送实际由 `BeltSimulationLogic` 主线程处理）
- worker 的 `_beltEnd` / `_pushOutputToBelts`
- protocol 的 `SimControlMessage`（双方实际用裸 Map 通信）

**测试**:
- 新增 `test/canvas/main_thread_simulation_backend_test.dart`（7 个冒烟测试），
  覆盖生产循环、输入不足阻塞、输出上限拒绝、传送带推进与回绕、`onChanged` 回调。
- 现有 68 个测试全部通过；总计 75 个测试通过。

**预期收益**（已实现）:
- 主文件从 552 行降到 ~120 行，职责单一
- 两条执行路径物理隔离，可独立测试
- 添加新平台（如 Worker）只需新增一个 `SimulationBackend` 实现

**工作量**: 实际 ~1 天

Future<void> _precacheSvg(String path) async {

// lib/utils/error_handler.dart
enum ErrorSeverity { info, warning, error, critical }

  final String? code;
  final StackTrace? stackTrace;
