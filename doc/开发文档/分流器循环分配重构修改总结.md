# 分流器循环分配重构修改总结

## 修改日期
2026-06-21（后续修复持续进行）

## 修改背景

分流器（Splitter）是 1x1 物流设备，输入端在下方，输出端在左、上、右三个方向。其功能是将 1 条输入传送带的物品均匀分配到最多 3 条输出传送带。

### 用户需求

1. **循环分配**：物品按输出传送带创建顺序循环传输，不是填满一条再填下一条
2. **跳过无传送带方向**：如果某方向无传送带，跳过该端口继续下一个
3. **跳过满传送带**：如果某方向传送带满了，跳过该方向分配到下一个
4. **所有输出满时阻塞输入端**：当所有输出传送带均无法接收物品时，输入端传送带堵塞，物品在传送带上排队等待
5. **物品动画自然流动**：物品到达停止位置时，从格子入口自然流动到格子中央，而非瞬移
6. **禁止往输入端创建传送带**：从分流器创建传送带时，禁止往下方（输入端方向）拖拽，预览显示红色

### 分配逻辑示例

- **3 条带全通**：物品1→左, 物品2→上, 物品3→右, 物品4→左...（6 秒一轮）
- **2 条带（左+右）**：物品1→左, 物品2→右, 物品3→左...（4 秒一轮，跳过上）
- **左边满了**：物品4 跳过左→上, 物品5→右, 物品6→上...（4 秒一轮）
- **全部满了**：输入端堵塞，物品在输入传送带上排队

## 架构变更：拉取式（Slot 中转）→ 推送式（直接推送）

### 旧架构（拉取式 / Slot 中转）

```
输入带 tick → 物品到达末端 → 分流器接收物品（放入 slot 缓冲）
                                    ↓
输出带 tick → 查询 slot（方向匹配） → 拉取物品 → 塞到输出带开头
```

问题：需要 slot 缓冲中转，物品在 slot 中等待输出带 tick；slot 满时最多再缓存 1 个，之后虽然阻塞但用户仍看到有物品"进入分流器内部"。

### 新架构（推送式 / 直接推送）

```
输入带 tick → 物品到达末端 → 分流器直接推送到输出带（左→上→右循环）
                                    ↓
                    左边有空？→ 推送成功
                    左边满了？→ 试上边 → 有空？→ 推送成功
                    上都满了？→ 试右边 → 有空？→ 推送成功
                    全满了？→ 返回 false → 输入端堵塞
```

优势：
- 无 slot 中转延迟，实时跳过满传送带
- 所有输出满时直接阻塞输入端，物品在传送带上排队
- 无"物品进入分流器内部"的歧义

## project.dart 修改详情

### 1. `_mergeAdjacentSegments` — 物品段合并增加 freezeProgress 匹配条件

**修改原因**：两个 freezeProgress 不同的段合并时，会互相破坏对方的冻结状态：
- 保留前方段的 `fp=0.5` → 后方刚到的物品被提前冻结（瞬移到格子中央）
- 清空 fp → 前方已冻结的物品被解冻（突然跳动）

**修改后**：仅当两段的 `freezeProgress` 完全相等时才合拼。不同冻结状态的段保持独立，各自经历完整的冻结过渡。

```dart
void _mergeAdjacentSegments() {
    ...
    if (prev.itemId == segment.itemId &&
        prev.fillCount >= segment.drainCount &&
        prev.freezeProgress == segment.freezeProgress) {  // ← 新增条件
        // 合拼
        if (segment.fillCount > prev.fillCount) prev.fillCount = segment.fillCount;
        if (segment.drainCount < prev.drainCount) prev.drainCount = segment.drainCount;
        continue;
    }
}
```

### 2. `canAcceptNewItemFromStart` — 死胡同满带判据修复

**问题**：死胡同传送带上的物品推进到末端（`fillCount == path.length`）但 `drainCount > 0` 时（起始端有"空位"），`canAcceptNewItemFromStart` 仍返回 true。分流器推送新物品后被冻结并与已有段合并，合并后 `drainCount` 减小又使 canAccept 变 true，形成"推送→合并→再推送"循环，用户看到物品反复出现后消失。

**修复**：当 `fillCount >= endLimit` 且 `terminalLimit == null`（死胡同）且 `drainCount <= 1` 时拒绝接收。`drainCount <= 1` 意味着仅剩 position 0（建筑遮挡隐藏格）可用，新物品插入后会立即冻结合并消失。`drainCount >= 2` 时仍有可见格，允许接收。

```dart
bool canAcceptNewItemFromStart(String itemId, {int? terminalLimit}) {
    ...
    if (first.fillCount >= endLimit && terminalLimit == null && first.drainCount <= 1) {
        return false;
    }
    return first.drainCount > 0;
}
```

### 3. `ConveyorItemSegment.skipAdvanceOnce` — 分流器推送瞬移延迟

**问题**：分流器推送物品到输出带时，物品在 position 0（被建筑遮挡的格子）创建。输出带的下一次 tick 立即将其推进到 position 1（第一个可见格子），玩家看到物品从分流器"瞬移"到传送带起点，没有从建筑边缘逐渐出现的过渡。

**修复**：在 `ConveyorItemSegment` 中新增 `skipAdvanceOnce` 标志（默认 false）。分流器推送时设为 true，`_tickSingleBeltOnce` 检测到该标志后清除但跳过本 tick 的推进，使物品在 position 0 停留一个 tick 周期让玩家看到从建筑边缘逐渐出现的过渡。

```dart
class ConveyorItemSegment {
    ...
    bool skipAdvanceOnce;  // ← 新增字段
}

// pushSourceItem 签名扩展
bool pushSourceItem(String sourceItemId, {int? terminalLimit, bool skipAdvanceOnce = false}) {
    // 创建新段时传入 skipAdvanceOnce
    itemSegments.add(ConveyorItemSegment(
        itemId: sourceItemId, fillCount: 1.clamp(0, endLimit).toInt(),
        skipAdvanceOnce: skipAdvanceOnce,
    ));
}
```

## canvas_editor.dart 修改详情

### 1. 分流器架构：从拉取式改为推送式

#### `_canBeltOutputEnterBuilding` 分流器分支

**修改前（拉取式/Slot）**：
```dart
if (building.isSplitter) {
    if (building.splitterBufferOccupied) return false;
    return _getConnectedSplitterOutputDirections(building).isNotEmpty;
}
```

**修改后（推送式）**：
```dart
if (building.isSplitter) {
    final connectedDirs = _getConnectedSplitterOutputDirections(building);
    if (connectedDirs.isEmpty) return false;
    for (final dir in connectedDirs) {
        final outputBelt = _getBeltForSplitterOutputDirection(building, dir);
        if (outputBelt != null && _canSplitterOutputBeltAcceptItem(outputBelt, itemId)) {
            return true;
        }
    }
    return false;  // 所有输出满，直接阻塞
}
```

#### `_transferBeltOutputToBuilding` 分流器分支

**修改前（拉取式/Slot）**：
- 先调用 `_drainSplitterBuffer` 排空缓冲
- 查找可用方向 → 放入 slot 缓冲
- slot 满时阻塞，并尝试将缓冲物品排出

**修改后（推送式）**：
- 不再使用 slot 缓冲，移除 `_drainSplitterBuffer` 调用
- 查找可用方向 → 直接 `pushSourceItem` 到输出传送带
- 所有输出满时直接返回 false，输入端堵塞

```dart
if (building.isSplitter) {
    final direction = _findNextAvailableSplitterDirection(building, itemId);
    if (direction != null) {
        final outputBelt = _getBeltForSplitterOutputDirection(building, direction);
        if (outputBelt != null) {
            final terminalLimit = _calculateBeltTerminalLimit(outputBelt);
            if (outputBelt.pushSourceItem(itemId, terminalLimit: terminalLimit)) {
                belt.removeOutputReadyItem();
                return true;
            }
        }
        // 推送失败：回退 cycleIndex
        const cycleOrder = ['left', 'up', 'right'];
        final idx = cycleOrder.indexOf(direction);
        if (idx >= 0) building.splitterCycleIndex = idx;
    }
    return false;  // 所有输出不可用，阻塞
}
```

### 2. `_freezeReadyOutputSegments` — 按物品段独立上限冻结

**修改原因**：原代码对所有物品段使用同一个 `freezeLimit`（传送带末端位置），导致只有到达尽头的物品才会被冻结。被前方物品挡住的中间物品不会冻结，其位置随 `arrowProgress` 抖动。

**修改后**：为每个物品段计算独立的冻结上限：
- 最后一段的上限 = 终端极限值（传送带尽头/阻塞位置）
- 前方段落的上限 = 下一段的 `drainCount`（不能越过前面的物品）

```dart
void _freezeReadyOutputSegments(ConveyorBelt belt, {required int limit}) {
    ...
    for (int i = 0; i < belt.itemSegments.length; i++) {
        final segLimit = i + 1 < belt.itemSegments.length
            ? belt.itemSegments[i + 1].drainCount.clamp(0, belt.path.length).toInt()
            : endLimit;
        if (segment.fillCount >= segLimit && segment.freezeProgress == null) {
            segment.freezeProgress = -1.0;
        }
    }
}
```

### 3. `_canSplitterOutputBeltAcceptItem` — 分流器输出带可用性检查

综合考虑传送带起始端空间和末端阻塞情况，判断输出传送带是否可以接收新物品。

```dart
bool _canSplitterOutputBeltAcceptItem(ConveyorBelt belt, String itemId) {
    if (belt.path.isEmpty || itemId.isEmpty) return false;
    final isDeadEnd = ...;
    final inputBuilding = ...;
    final inputBlocked = ...;
    final terminalLimit = inputBlocked ? belt.path.length - 1 : null;
    return belt.canAcceptNewItemFromStart(itemId, terminalLimit: terminalLimit);

```

### 4. `_tickSingleBeltOnce` — 处理 skipAdvanceOnce 延迟推进

分流器推送时设置了 `skipAdvanceOnce: true`，`_tickSingleBeltOnce` 在检测到该标志时不对物品设置 `activeSourceItemId`（跳过推进），仅清除标志使下一个 tick 恢复正常。

```dart
if (!isProducing && belt.itemSegments.isNotEmpty) {
    final firstSegment = belt.itemSegments.first;
    if (firstSegment.drainCount == 0) {
        if (firstSegment.skipAdvanceOnce) {
            firstSegment.skipAdvanceOnce = false;  // 延迟一帧，不清除推进
        } else {
            final sourceBuilding = _findOutputBuildingAtCell(belt.path.first);
            if (sourceBuilding != null && sourceBuilding.isSplitter) {
                activeSourceItemId = firstSegment.itemId;
            }
        }
    }
}
```

### 5. `_transferBeltOutputToBuilding` — 分流器推送设置 skipAdvanceOnce

```dart
if (outputBelt.pushSourceItem(itemId, terminalLimit: terminalLimit, skipAdvanceOnce: true)) {
    belt.removeOutputReadyItem();
    return true;
}
```

### 6. 分流器分发顺序：固定顺序 → 创建顺序

**修改原因**：原分流器始终按硬编码的 `左→上→右` 顺序分发物品，与输出传送带的创建顺序无关。用户希望在先创建右边传送带时，物品优先分配到右边。

**修复**：4 处 `const cycleOrder = ['left', 'up', 'right']` 全部替换为 `_getConnectedSplitterOutputDirections()` 的动态返回结果。`_getConnectedSplitterOutputDirections` 遍历 `_project.conveyors`（按创建顺序），自然返回创建顺序的方向列表。`splitterCycleIndex` 对动态列表长度取模。

受影响的函数：`_peekNextAvailableSplitterDirection`、`_findNextAvailableSplitterDirection`、`_drainSplitterBuffer`、`_transferBeltOutputToBuilding` 推送失败回滚。

## transport_belt_renderer.dart 修改详情

### 1. 冻结过渡：两阶段 → 三阶段状态机

**修改原因**：原冻结过渡 `null → -1.0 → 0.5` 在 `arrowProgress >= 0.5` 时会在同一帧内完成，导致物品瞬间从"流动中"跳到"格子中央"。

**修改后**：三阶段状态机确保物品总是经历完整的"入口→中央"流动过程：

```
null → -1.0 → (等 arrowProgress < 0.5) → -0.5 → (等 arrowProgress >= 0.5) → 0.5
  流动    刚到达停止位           通过入口半区               到达格子中央         冻结
```

| 状态 | 含义 |
|------|------|
| `null` | 未冻结，随 arrowProgress 流动 |
| `-1.0` | 刚到达停止位，等待 arrowProgress < 0.5（通过入口半区） |
| `-0.5` | 已通过入口半区，等待 arrowProgress >= 0.5（到达格子中央） |
| `0.5` | 冻结在格子中央 |

```dart
if (shouldFreezeSegment && sourceSegment.freezeProgress == null) {
    sourceSegment.freezeProgress = -1.0;           // 阶段 0→1
}
if (shouldFreezeSegment && sourceSegment.freezeProgress == -1.0) {
    if (arrowProgress < 0.5) {
        sourceSegment.freezeProgress = -0.5;       // 阶段 1→2
    }
}
if (shouldFreezeSegment && sourceSegment.freezeProgress == -0.5) {
    if (arrowProgress >= 0.5) {
        sourceSegment.freezeProgress = 0.5;        // 阶段 2→3
    }
}
```

同样的三阶段过渡也应用于遗留路径的 `deadEndFreezeProgress` 和 `lastItemFreezeProgress`。

### 2. `shouldFreezeSegment` — 移除 `isDeadEnd` 依赖

**修改前**：`shouldFreezeSegment` 需要 `isDeadEnd` 为 true，导致连接到建筑物的传送带上的中间物品不会被冻结。

**修改后**：物品到达各自独立上限（`segment.fillCount >= limit`）即冻结，无论传送带是否连接建筑物。

## transport_belt.dart 修改详情

### 1. 传送带创建方向限制修复

**问题**：未连接输入传送带的分流器，只能往上/下方向创建传送带，不能往左/右方向。必须先创建输入传送带，才能正常创建左/右方向的输出传送带。

**根因**：`_handleFirstAnchor` 中，当分流器无已有传送带时，`_findPortAtCell` 返回第一个匹配的输出端口（分流器端口定义顺序为 `[up, left, right]`，总是 `up`），然后 `_startingPortDirection` 被设为 `up`，限制了初始方向只能往上/下。

当已有输入传送带时，代码走 `_findBeltAtCell` 分支，`_startingPortDirection = null`（无约束），所有方向可用。

**修复**：统一行为——从输出端口创建传送带时，`_startingPortDirection = null`，不限制方向。

```dart
// 修改前
_startingPortDirection = portInfo.worldDirection;  // 限制为端口方向

// 修改后
_startingPortDirection = null;  // 不限制方向，允许左/上/右任意选择
```

### 2. `_handleSubsequentAnchor` — 建筑输入端口检测修复

**问题**：先创建分流器的输出传送带（左、上、右）后，无法创建输入传送带。点击分流器格子无响应。同时，当分流器和已有传送带一起时，首次点击可往下方（输入端方向）拖拽创建传送带。

**根因**：

1. **`_findPortAtCell` 对 1x1 建筑无效**：`PortDefinition.gridPosition` 为 1x1 建筑计算端口坐标时，所有端口（输入和三个输出）都映射到建筑格中心 `(gridX+0.5, gridY+0.5)`，round 后为 `(gridX+1, gridY+1)`。而 `_isCellDeviceInputPort` 用 `gridPosition.round()` 与点击格比较，永远匹配不上 `(gridX, gridY)`。

2. **mergeBelt 和 midBelt 双重拦截**：`_handleSubsequentAnchor` 中，先检测 mergeBelt（已有传送带起点合并），再检测 midBelt（已有传送带中间截断）。两个检查都会在发现分流器格子上已有输出传送带时 `return false`，代码永远到不了下方的 `isInputPort` 终点连接逻辑。

**修复**：

1. 新增 `_buildingAtCellHasInputPort` 函数：改为直接遍历建筑列表，按 `effectiveGridX/effectiveGridY/effectiveWidth/effectiveHeight` 检查目标格子是否被有输入端口的建筑占据，不依赖端口坐标。

```dart
bool _buildingAtCellHasInputPort(Offset gridPos) {
    final gx = gridPos.dx.toInt();
    final gy = gridPos.dy.toInt();
    for (final pb in project.buildings) {
        if (pb.inputPorts.isEmpty) continue;
        final bx = pb.effectiveGridX.toInt();
        final by = pb.effectiveGridY.toInt();
        if (gx >= bx && gx < bx + pb.effectiveWidth &&
            gy >= by && gy < by + pb.effectiveHeight) {
            return true;
        }
    }
    return false;
}
```

2. 在 `_handleSubsequentAnchor` 中，将建筑输入端口检测提前到 mergeBelt 和 midBelt 检查之前。当 `_isCellInBuilding && _buildingAtCellHasInputPort` 为 true 时，直接跳过两个检查，让代码进入下方的 isInputPort 终点连接逻辑。

3. 在 `isInputPort` 判据中追加 `_buildingAtCellHasInputPort` 作为 `_isCellDeviceInputPort` 的补检，确保 1x1 建筑格被正确识别为合法的传送带终点。

```dart
final isBuildingInputCell =
    _isCellInBuilding(gridPos) && _buildingAtCellHasInputPort(gridPos);
if (!isBuildingInputCell) {
    // mergeBelt 和 midBelt 检查...
}
// isInputPort 判据加入补检
final isInputPort = _isCellDeviceInputPort(gridPos) ||
    (_isCellInBuilding(gridPos) && _buildingAtCellHasInputPort(gridPos));
```

### 3. 输出端口方向限制 — 禁止往输入端（下方）创建传送带

**问题**：仅放置分流器后，从分流器创建输出传送带时，可往下方（输入端方向）拖拽创建，预览显示蓝色（有效）。下方是分流器输入端，不应允许往该方向创建。

**根因**：`_handleFirstAnchor` 将 `_startingPortDirection = null`（无限制），BFS 路径搜索允许全部 4 个方向。单值 `String?` 的 `_startingPortDirection` 无法表达「允许多个方向但禁止特定方向」。

**修复**：

1. 新增 `_startingPortAllowedDirections`（`Set<String>?`）字段，表达多方向允许集合。

2. 新增 `_computeAllowedDirectionsForBuilding` 函数：遍历建筑输出端口，计算旋转后的世界方向集合。分流器返回 `{up, left, right}`。

3. `_findPath` 验证动量路径首段方向是否在允许集合内。若不在，标记无效回退到 BFS。

4. `_findPathBFS` 优先使用 `allowedDirections` 限制起始节点的可探索方向。无 `allowedDirections` 时回退到原有单方向逻辑。

## 架构总结

```
                          ┌──────────────────────────┐
                          │      Splitter (1x1)      │
                          │                          │
   Input Belt ──────────→ │  input                   │
                          │                          │
                          │  cycle: 创建顺序          │
                          │         ↓  ↓  ↓          │
                          │  按创建顺序跳过满传送带    │
                          │                          │
                          │  全满 → BLOCKED          │
                          └──────────────────────────┘
                                    ↓ direct push
                          ┌──────────────────────────┐
                          │    Output Belts          │
                          │  (dead-end, fill from    │
                          │   end to start)          │
                          └──────────────────────────┘
```

- **分流器**：纯推送式，无内部缓冲。按输出传送带创建顺序循环分发；全满 → 阻塞输入端
- **传送带物品冻结**：按物品段独立上限冻结，三阶段过渡（-1.0 → -0.5 → 0.5）保证自然流动
- **物品段合并**：仅合并相同 freezeProgress 的相邻段，保护各自的冻结状态
- **传送带创建**：从输出端口创建时不限制方向，允许左/上/右任意选择
- **输出带满判据**：`canAcceptNewItemFromStart` 仅在 `drainCount <= 1`（仅剩隐藏格）时拒绝死胡同传送带接收新物品
- **推送瞬移延迟**：`skipAdvanceOnce` 使物品在 position 0 停留 1 tick，避免从建筑遮挡格瞬移到可见格
- **建筑端口检测**：`_buildingAtCellHasInputPort` 通过建筑占据范围判断，解决 `_findPortAtCell` 对 1x1 建筑的坐标偏差问题
- **输出端口方向限制**：`_startingPortAllowedDirections` + BFS 方向过滤，阻止从建筑输出端口往输入端方向创建传送带
