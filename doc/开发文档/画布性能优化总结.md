# 画布性能优化总结

## 一、问题背景

在画布编辑器中放置 40+ 设备和 17 条传送带后，缩放到最小并旋转画布时出现明显掉帧。同时设备创建时存在约 300ms 的延迟。

测试环境：Flutter Web (Chrome)，`flutter run -d chrome`

## 二、问题诊断

### 2.1 设备创建延迟

**根因**：`GestureDetector` 同时注册了 `onTapUp` 和 `onDoubleTapDown`，Flutter 手势竞技场需要等待约 300ms（`kDoubleTapTimeout`）才能确认是单击还是双击的第一下。等待期间 `placingBuilding` 未被清除，预览继续跟随鼠标。

**修复**：将单击/双击处理从 `GestureDetector` 移到 `Listener.onPointerDown`，使用手动双击检测（时间戳 + 位置距离判断），单击在 `onPointerDown` 时立即执行。

### 2.2 旋转掉帧

通过添加分段计时日志定位瓶颈：

```
[Paint] scale=0.250 | angle=558.0° | grid=0μs conveyor=1699μs building=5701μs preview=0μs | total=7400μs
```

| 渲染阶段 | 平均耗时 | 占比 |
|---------|---------|------|
| grid（网格） | ~50μs | <1% |
| conveyor（传送带） | ~1.8ms | ~25% |
| **building（设备）** | **~5.4ms** | **~70%** |
| preview（预览） | ~0μs | 0% |

**设备渲染是主要瓶颈**，每设备约 122μs，根因是 Flutter Web 的 Dart→JS→WebGL 跨界调用开销。

### 2.3 端口连接重复计算

每次 `paint()` 都重新计算所有端口连接关系，复杂度 O(buildings × conveyors × ports)，在设备/传送带数量多时开销显著。

**修复**：将端口连接计算结果缓存到 `_portConnectionsCache`，仅在数据变更时重建。

## 三、已实施的优化

### 3.1 手动双击检测（消除创建延迟）

- 位置：`canvas_editor.dart` 的 `Listener.onPointerDown`
- 效果：设备创建从 300ms 延迟降为即时响应

### 3.2 端口连接缓存

- 位置：`CanvasEditorState._portConnectionsCache`
- 触发时机：`initState`、`_placeBuilding`、`_placeConveyorPath`、`didUpdateWidget`
- 效果：消除每帧 O(buildings × conveyors × ports) 的重复计算

### 3.3 onHover 优化

- 位置：`MouseRegion.onHover`
- 逻辑：只在鼠标网格位置实际变化时才 `setState`
- 效果：减少同一格内的无效重绘

### 3.4 视口裁剪（Viewport Culling）

- 位置：`_EditorPainter._computeViewport()` / `_isBuildingVisible()` / `_isBeltVisible()`
- 逻辑：将屏幕四角逆变换到世界坐标，计算可见区域，跳过屏幕外的对象
- 注意：`belt.start/end` 已经是像素坐标（getter 内部已乘 cellSize），裁剪时无需再乘

### 3.5 LOD（Level of Detail）三级细节

| 缩放范围 | detailLevel | 设备渲染内容 | 传送带渲染内容 |
|---------|-------------|-------------|--------------|
| scale < 0.35 | 0 (minimal) | 仅色块+边框 | 仅色块矩形 |
| 0.35 ≤ scale < 0.5 | 1 (simplified) | +网格线+进度条 | +中心线+箭头 |
| scale ≥ 0.5 | 2 (full) | +端口+文字+配方 | +粒子动画 |

所有渲染器（BuildingRenderer、RefiningUnitRenderer、DepotAccessRenderer、ConveyorRenderer）均已支持 `detailLevel` 参数。

### 3.6 预渲染缓存（Picture Cache）

- 位置：`_EditorPainter._pictureCache`
- 逻辑：将每个设备的静态部分渲染一次到 `ui.Picture`，后续帧直接 `canvas.drawPicture()`
- 缓存 key：`buildingId_rotation_detailLevel_portsHash`
- 缓存上限：200 个 Picture
- 动态部分（进度条）不缓存，每帧绘制
- 效果：避免每帧重复创建 Paint/TextPainter/Path

## 四、各平台性能差异

| 平台 | 渲染后端 | 性能 | 说明 |
|------|---------|------|------|
| Web (Chrome) | CanvasKit (WebGL) | 最慢 | Dart→JS→WebGL 跨界开销大 |
| Web (Chrome, html renderer) | HTML+CSS | 更慢 | 不推荐 |
| **Windows** | **Skia (C++)** | **快 5-10 倍** | Dart 直接调用 Skia，无跨界 |
| **Android** | **Skia (C++)** | **快 5-10 倍** | 同上 |

实测：41 个设备在 Windows 端旋转画布无掉帧，Web 端 scale=0.5 时仍有 5ms/帧。

**结论**：当前性能问题仅存在于 Web 端，Windows/Android 客户端无需担忧。

## 五、SVG 替换方案评估

后期设备占位符会替换为精致的 SVG 图片，评估结论：

| 方案 | Web性能 | 客户端性能 | 说明 |
|------|--------|-----------|------|
| 当前 Canvas 手绘 | 中 | 优 | 已有 Picture 缓存 |
| SVG (flutter_svg) | 中 | 优 | Picture 缓存同样有效，首次解析略慢 |
| SVG + 预解析为 DrawableRoot | 中 | 优 | 避免每帧重新解析 XML |

**结论**：在 Windows/Android 客户端上，复杂 SVG 不会有性能问题。原因：
1. Skia 直接渲染，无跨界开销
2. Picture 缓存机制对 SVG 同样有效，渲染结果会被缓存
3. 即使一个 SVG 有 50-100 个 Path，在 Skia 上单帧耗时约 0.5-1ms

**注意事项**：
- 用 `flutter_svg` 时应预解析为 `DrawableRoot`，避免每帧重新解析 SVG XML
- 继续使用 Picture 缓存机制，SVG 渲染结果同样会被缓存

## 六、后续优化路线

### 6.1 ui.Image 预光栅化（按需实施）

当前 Picture 缓存是矢量回放，每帧仍需逐条回放 draw call。如果未来对象数量达到数百个，可将 Picture 转为 `ui.Image`（通过 `Picture.toImage()`），每设备只需 1 次 `drawImage`。

- 优点：draw call 从 20-30 次/设备 降为 1 次/设备
- 缺点：缩放时可能模糊/锯齿，需按缩放级别生成多套缓存
- 建议：先测试当前 Picture 缓存方案，如果够用就不需要走这一步

### 6.2 Isolate 计算分离（必须实施）

当前 `SimulationEngine` 在主 Isolate 运行，生产计算会阻塞 UI 线程。

```
当前：主Isolate = UI渲染 + 生产计算 → 互相争抢 → 掉帧
优化后：主Isolate = UI渲染，计算Isolate = 生产计算 → 互不干扰
```

- Dart Isolate 在 Web 上映射为 Web Worker，在原生平台上是真正的线程
- 100+ 设备的生产计算放在独立 Isolate，每秒向主 Isolate 推送一次计算结果
- UI 线程完全不受影响

### 6.3 优化优先级

1. **Isolate 计算分离** — 生产计算功能开发前必须完成
2. **ui.Image 预光栅化** — 仅在 Web 端性能仍不满足时实施
3. **SVG 预解析** — 替换占位符时同步实施

日志字段说明：
- `grid/conveyor/building/preview`：各渲染阶段耗时（微秒）
- `visible=X/Y+Z/W`：实际渲染数/总数（设备+传送带）
- `lod=N`：当前细节层级（0/1/2）

## 八、关键经验教训

1. **Flutter Web 是性能最差的平台**，性能测试应以 Web 端为基准，Windows/Android 端通常无需担忧
2. **GestureDetector 的 onTapUp + onDoubleTapDown 组合会导致 300ms 延迟**，需要手动双击检测替代
3. **belt.start/end 是像素坐标**，不是网格坐标，视口裁剪时无需再乘 cellSize
4. **端口连接计算应缓存**，不应在每帧 paint 中重复计算
5. **Picture 缓存对 SVG 同样有效**，SVG 替换占位符时无需额外架构调整
6. **生产计算必须移入 Isolate**，否则会阻塞 UI 线程导致掉帧
