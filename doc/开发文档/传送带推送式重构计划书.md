# 传送带推送式重构计划书

## 文档信息
- 创建日期：2026-06-21
- 涉及设备：分流器（Splitter）
- 重构目标：将分流器从拉取式（Slot 中转）改为推送式（直接推送）

---

## 一、背景与目标

### 1.1 当前问题

当前分流器采用**拉取式**架构，通过 slot 中转物品：

```
输入带 tick → 物品进入分流器 slot（绑定方向）
                    ↓（等待）
输出带 tick → 查询 slot → 拉取物品 → 压入输出带开头
```

存在以下问题：
1. **Slot 中转延迟**：物品需在 slot 中等待输出带 tick，造成 1 tick（2秒）延迟
2. **方向锁定**：物品进入 slot 后方向固定，如果该方向输出带在拉取前变满，物品卡在 slot
3. **时序依赖**：输入带和输出带的 tick 顺序影响物品流转效率
4. **循环分配失效**：物品已绑定方向，无法动态跳过满传送带

### 1.2 重构目标

改为**推送式**架构，分流器接收物品后直接推送到输出带：

```
输入带 tick → 物品到达末端 → 分流器接收
                                    ↓
                    分流器主动尝试推送到输出带
                    ↓
              左边满了？试上边 → 上边满了？试右边
              ↓
            成功 → 物品直接进入输出带开头
            全满 → 物品留在输入带（阻塞）
```

### 1.3 核心原则

**传送带动画系统保持不变**。推送式只改变物品如何进入传送带开头，不改变物品在传送带上的移动和渲染逻辑。

## 二、当前架构分析

### 2.1 传送带 Tick 机制

每条传送带每 **2秒** tick 一次，由 `arrowProgress` 跨零检测触发（`_onBeltAnimationFrame`）。

每条传送带有独立的 `phaseOffset`，决定 tick 时刻，各传送带 tick 时刻错开。

### 2.2 单条传送带 Tick 流程（`_tickSingleBeltOnce`）

```
1. 计算末端状态
   - isDeadEnd：末端是否为死胡同
   - inputBuilding：末端连接的建筑
   - inputBlocked：末端建筑是否无法接收物品
   - terminalLimit：末端阻塞时限制物品前进位置

2. 查询源建筑（_getAvailableOutputItemIdForBeltStart）
   - 查询起点建筑是否有物品可提供
   - 分流器：查询 slot 中的物品（方向匹配）

3. 压入物品（pushSourceItem）
   - 将物品压入传送带开头（itemSegments 位置 0）
   - 内部判断首格是否可接受

4. 消费源物品（_consumeOutputItemForBeltStart）
   - 从源建筑消费物品
   - 分流器：消费 slot 中的物品

5. 推进物品（advanceItemSegments）
   - 所有物品前进一格
   - activeSourceItemId：源建筑正在提供的物品 ID
   - 如果 segment.drainCount == 0 且 itemId == activeSourceItemId，
     跳过该 segment（物品保持在位置 0，不前进）

6. 转移末端物品（_transferBeltOutputToBuilding）
   - 末端物品转移给连接的建筑
   - 分流器：物品进入 slot（绑定方向）
```

### 2.3 传送带动画渲染机制

渲染器：`transport_belt_renderer.dart` 第 466-475 行

```dart
final renderSegments = belt.itemSegments
    .where((segment) => segment.hasItems)
    .map((segment) => ConveyorItemSegment(
          itemId: segment.itemId,
          fillCount: segment.fillCount.clamp(0, belt.path.length).toInt(),
          drainCount: segment.drainCount.clamp(0, belt.path.length).toInt(),
          freezeProgress: segment.freezeProgress,
        ))
    .toList()
  ..sort((a, b) => a.drainCount.compareTo(b.drainCount));
```

**动画数据来源**：
- `itemSegments`：物品段列表，每段包含 `itemId`、`fillCount`、`drainCount`、`freezeProgress`
- `arrowProgress`：由 `animationProgress(globalProgress)` 计算，基于 `phaseOffset`
- 物品位置 `i` 存在条件：`drainCount <= i < fillCount`

**动画驱动**：
- `arrowProgress` 从 0→1 循环，每 2 秒一个周期
- `arrowProgress` 跨越 0.5 时触发 tick（`_onBeltAnimationFrame` 第 408 行）
- 渲染时 `arrowProgress` 驱动物品在格子内的视觉移动

### 2.4 关键方法：`pushSourceItem`（project.dart 第 695-734 行）

```dart

  // 1. 空传送带：创建新 segment（fillCount=1, drainCount=0）
```


**`activeSourceItemId` 的作用**：

## 三、推送式架构设计

### 3.1 核心思路

分流器在**输入带 tick 时**直接调用输出带的 `pushSourceItem`，物品不经过 slot 中转。

```
输入带 tick → _transferBeltOutputToBuilding（分流器分支）
                                    ↓
          _findNextAvailableSplitterDirection（循环分配）
                                    ↓
          outputBelt.pushSourceItem(itemId)  ← 直接推送
                                    ↓
          成功 → inputBelt.removeOutputReadyItem()
          失败 → 试下一个方向 / 全满则返回 false（输入带阻塞）
```

### 3.2 动画保持不变的原因

| 关注点 | 分析 | 是否需要改 |
|--------|------|-----------|
| `itemSegments` 数据结构 | 推送式调用 `pushSourceItem` 修改 `itemSegments`，与拉取式相同 | 否 |
| `arrowProgress` 动画驱动 | 基于 `phaseOffset` 和 `globalProgress`，与推送/拉取无关 | 否 |
| `advanceItemSegments` 物品推进 | 仍由各传送带自己的 tick 调用，逻辑不变 | 否 |
| `freezeProgress` 冻结机制 | 死胡同/阻塞冻结逻辑不变 | 否 |
| 渲染器 `transport_belt_renderer.dart` | 只读 `itemSegments` 渲染，不关心物品来源 | 否 |

**结论**：推送式只改变"谁调用 `pushSourceItem`"，不改变动画数据结构和渲染逻辑。

### 3.3 关键技术挑战：`activeSourceItemId` 行为差异

#### 拉取式行为（当前）

```
输出带 tick:
  1. _getAvailableOutputItemIdForBeltStart → 查询分流器 slot → 返回 itemId
  2. pushSourceItem(itemId) → 物品压入位置 0
  3. activeSourceItemId = itemId
  4. advanceItemSegments → 位置 0 的物品被保持（isFedBySource = true）
```

物品在位置 0 保持，直到源停止提供。

#### 推送式行为（拟改）

```
输入带 tick:
  1. 分流器调用 outputBelt.pushSourceItem(itemId) → 物品压入位置 0

输出带 tick:
  1. _getAvailableOutputItemIdForBeltStart → 查询分流器 → 返回 null（无 slot）
  2. 不调用 pushSourceItem
  3. activeSourceItemId = null
  4. advanceItemSegments → 位置 0 的物品前进（isFedBySource = false）
```

**问题**：位置 0 的物品会立即前进，可能导致物品在传送带上分散，而非累积在开头。

#### 解决方案

**方案 A：输出带 tick 时识别分流器源**

在输出带 tick 时，如果源建筑是分流器，设置 `activeSourceItemId` 为位置 0 物品的 ID（如果有）：

```dart
// _tickSingleBeltOnce 中
final sourceItemId = _getAvailableOutputItemIdForBeltStart(belt);
String? activeSourceItemId = sourceItemId;

// 推送式：如果源是分流器，且位置 0 有物品，保持该物品
if (sourceItemId == null && belt.itemSegments.isNotEmpty) {
  final firstSegment = belt.itemSegments.first;
  if (firstSegment.drainCount == 0) {
    final sourceBuilding = _findSourceBuildingAtCell(belt.path.first);
    if (sourceBuilding != null && sourceBuilding.isSplitter) {
      activeSourceItemId = firstSegment.itemId;
    }
  }
}
```

**优点**：保持与拉取式相同的动画行为（物品在位置 0 保持）
**缺点**：需要新增 `_findSourceBuildingAtCell` 辅助方法

**方案 B：不保持位置 0，让物品自然前进**

不设置 `activeSourceItemId`，物品在位置 0 前进到位置 1。

**优点**：逻辑简单，物品自然分散
**缺点**：动画行为与拉取式不同，物品不会累积在传送带开头

**推荐方案**：方案 A，保持动画一致性。

```dart
/// 计算传送带的末端阻塞限制
/// 用于分流器推送时确定输出带可接收物品的位置上限
int? _calculateBeltTerminalLimit(ConveyorBelt belt) {
  if (belt.path.isEmpty) return null;
  final isDeadEnd =
      !TransportBeltRenderer.isInputPort(belt.path.last, _project.buildings);
  final inputBuilding =
      isDeadEnd ? null : _findInputBuildingAtCell(belt.path.last);
  final pendingOutputItemId =
      inputBuilding == null ? null : belt.downstreamItemId();
  final inputBlocked = inputBuilding != null &&
      pendingOutputItemId != null &&
      !_canBeltOutputEnterBuilding(belt, inputBuilding, pendingOutputItemId);
  return inputBlocked ? belt.path.length - 1 : null;
}
```

```dart
/// 查找指定格子上的输出端口建筑（用于识别分流器源）
PlacedBuilding? _findOutputBuildingAtCell(Offset cell) {
  final gx = cell.dx.round();
  final gy = cell.dy.round();
  for (final pb in _project.buildings) {
    final rot = pb.rotation;
    final gw = pb.building.gridWidth;
    final gh = pb.building.gridHeight;
    for (final port in pb.outputPorts) {

      if (portCell.dx.round() == gx && portCell.dy.round() == gy) {
        return pb;
      }
    }
  }
  return null;
}
```

## 五、推送式工作流程

### 5.1 完整流程

```
输入带 tick（每 2 秒）:
  1. 查询源建筑 → 获取物品 itemId
  2. pushSourceItem(itemId) → 物品压入输入带开头
  3. 消费源建筑物品
  4. advanceItemSegments → 输入带上物品前进
  5. _transferBeltOutputToBuilding → 末端物品转移给分流器
     ↓（分流器分支）
     a. _findNextAvailableSplitterDirection(splitter, itemId)
        - 按 左→上→右 循环顺序
        - 跳过无传送带方向
        - 跳过满传送带（_canSplitterOutputBeltAcceptItem 检查）
        - 更新 splitterCycleIndex
     b. 获取输出带 outputBelt
     c. outputBelt.pushSourceItem(itemId) → 直接推送
     d. 成功 → inputBelt.removeOutputReadyItem()
     e. 失败 → 试下一个方向 / 全满则返回 false

输出带 tick（每 2 秒，独立 phaseOffset）:
  1. 查询源建筑（分流器）→ 返回 null（推送式无 slot）
  2. 不调用 pushSourceItem
  3. activeSourceItemId = 位置 0 物品 ID（方案 A，保持位置 0）
  4. advanceItemSegments → 物品前进（位置 0 保持，其他前进）
  5. 末端物品转移给连接的建筑
```

### 5.2 循环分配示例

**3 条输出带全通**：
```
t=0: 输入带 tick → 物品1 → 推送到左带（cycleIndex: 0→1）
t=2: 输入带 tick → 物品2 → 推送到上带（cycleIndex: 1→2）
t=4: 输入带 tick → 物品3 → 推送到右带（cycleIndex: 2→0）
t=6: 输入带 tick → 物品4 → 推送到左带（cycleIndex: 0→1）
...
3 条带一轮 = 6 秒
```

**2 条输出带（左+右，无上）**：
```
t=0: 物品1 → 左（跳过上，cycleIndex: 0→1）
t=2: 物品2 → 右（跳过上，cycleIndex: 2→0）
t=4: 物品3 → 左（cycleIndex: 0→1）
...
2 条带一轮 = 4 秒
```

**左边满了**：
```
t=0: 物品1 → 左（cycleIndex: 0→1）
t=2: 物品2 → 上（cycleIndex: 1→2）
t=4: 物品3 → 右（cycleIndex: 2→0）
t=6: 物品4 → 左满了，跳过 → 上（cycleIndex: 1→2）
t=8: 物品5 → 右（cycleIndex: 2→0）
t=10: 物品6 → 左满了，跳过 → 上（cycleIndex: 1→2）
...
2 条带一轮 = 4 秒
```

## 六、动画一致性验证

### 6.1 验证点 1：物品进入传送带开头

| 场景 | 拉取式 | 推送式 | 一致性 |
|------|--------|--------|--------|
| 物品出现在位置 0 | 输出带 tick 时 `pushSourceItem` | 输入带 tick 时 `pushSourceItem` | 数据结构相同 |
| `itemSegments` 修改 | 添加/扩展首段 | 添加/扩展首段 | 完全相同 |
| 渲染显示 | 位置 0 出现物品 | 位置 0 出现物品 | 完全相同 |

### 6.2 验证点 2：物品在传送带上移动

| 场景 | 拉取式 | 推送式 | 一致性 |
|------|--------|--------|--------|
| `advanceItemSegments` 调用 | 输出带 tick 时 | 输出带 tick 时 | 完全相同 |
| 位置 0 物品保持 | `activeSourceItemId` 设置 | 方案 A 设置 `activeSourceItemId` | 一致 |
| 其他位置物品前进 | `drainCount++` | `drainCount++` | 完全相同 |
| `arrowProgress` 驱动 | 基于 `phaseOffset` | 基于 `phaseOffset` | 完全相同 |

### 6.3 验证点 3：死胡同/阻塞冻结

| 场景 | 拉取式 | 推送式 | 一致性 |
|------|--------|--------|--------|
| `freezeDeadEndSegments` | 输出带 tick 时调用 | 输出带 tick 时调用 | 完全相同 |
| `freezeProgress` 设置 | 基于 `fillCount` 和 `limit` | 基于 `fillCount` 和 `limit` | 完全相同 |
| `_freezeReadyOutputSegments` | 末端阻塞时调用 | 末端阻塞时调用 | 完全相同 |

### 6.4 验证点 4：末端物品转移

|------|--------|--------|--------|
| 输出带末端物品转移 | `_transferBeltOutputToBuilding` | `_transferBeltOutputToBuilding` | 完全相同 |
| 转移给生产设备/仓库 | 逻辑不变 | 逻辑不变 | 完全相同 |

### 6.5 结论

**动画系统完全不需要修改**。推送式只改变物品进入传送带开头的时机和调用者，不改变：
- `itemSegments` 数据结构
- `advanceItemSegments` 推进逻辑（通过方案 A 保持 `activeSourceItemId` 行为）
- `arrowProgress` 动画驱动

- 渲染器读取逻辑

## 八、风险与注意事项

### 8.1 时序问题

输入带和输出带的 tick 时刻不同（不同 `phaseOffset`）。推送式在输入带 tick 时修改输出带状态，输出带 tick 时读取该状态。

**风险**：如果输出带 tick 在输入带 tick 之前，物品还未推送，输出带位置 0 为空。
**缓解**：这是正常行为，物品会在下一次输出带 tick 时显示。动画无影响。

### 8.2 `activeSourceItemId` 方案 A 的边界情况

**情况**：输出带位置 0 有物品，但分流器已经停止推送（输入带无物品）。
**行为**：方案 A 会错误地保持位置 0 物品（`activeSourceItemId` 非空）。
**缓解**：需要检查分流器是否仍有物品流入。如果输入带无物品到达分流器，不设置 `activeSourceItemId`。

**改进方案**：
```dart
if (!isProducing && belt.itemSegments.isNotEmpty) {
  final firstSegment = belt.itemSegments.first;
  if (firstSegment.drainCount == 0) {
    final sourceBuilding = _findOutputBuildingAtCell(belt.path.first);
    if (sourceBuilding != null && sourceBuilding.isSplitter) {
      // 检查分流器的输入带是否有物品正在到来
      if (_splitterHasIncomingItem(sourceBuilding)) {
        activeSourceItemId = firstSegment.itemId;
      }
    }
  }
}
```

### 8.3 多分流器串联

如果分流器的输出带连接到另一个分流器的输入端，推送式会递归推送。

**风险**：递归推送可能导致栈溢出或时序混乱。
**缓解**：`_transferBeltOutputToBuilding` 已经是递归安全的（推送成功即返回），不会无限递归。但需要测试验证。

## 十、总结

推送式重构的核心优势：
1. **移除 Slot 中转**：物品直接从输入带到输出带，无延迟
2. **实时跳过满带**：推送失败立即换方向，不卡死
3. **逻辑更简单**：移除 slot 机制，减少状态管理
4. **动画完全不变**：只改变调用 `pushSourceItem` 的时机和调用者

改动范围：
- `project.dart`：移除 slot 机制（简化）
- `canvas_editor.dart`：修改 4 个方法 + 新增 2 个辅助方法
- 动画系统：**零修改**
